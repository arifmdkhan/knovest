## 2. Workload formulas

**Database example:** 0.25 CU active continuously for a 730-hour month costs `0.25 × 730 × $0.106 = $19.35` compute. Five GB database storage adds `$1.75`, for **$21.10**, before history/branches/other usage. With only 120 active hours the same compute assumption becomes `$3.18`. These are scenarios, not observed utilization. Background polling may prevent scale-to-zero savings.

**Live usage:** `participant minutes = participants × minutes per session × sessions`. For 100 participants, 60 minutes and 20 monthly sessions, total is **120,000 participant minutes**. At 1,000 participants it is **1,200,000**. Count hosts/other billable participants according to provider rules.

For an unknown applicable video rate `r` dollars per 1,000 participant minutes:

| Workload | Gross usage cost at r=$1 (assumption) | At r=$2 (assumption) |
| --- | ---: | ---: |
| 120,000 participant minutes | $120 | $240 |
| 1,200,000 participant minutes | $1,200 | $2,400 |

The $1 and $2 values are sensitivity inputs, **not Stream HD quotes**. Apply confirmed credits once, after checking the account's eligible usage. Recording/captions/RTMP and overages remain additional.

**Prerecorded lessons:** the current FFmpeg ladder has approximately 9.2 Mb/s combined video plus 0.416 Mb/s audio. Nominal output for one source hour is `9.616 × 3600 / 8 / 1000 ≈ 4.33 GB`, before container overhead. This is an encoding-target estimate, not measured output. Raw uploads remain stored too. A 100-hour library therefore targets roughly **433 GB** of generated files before raw originals; at a conditional $0.023/GB-month, that is about **$9.96/month of storage alone**. Encoding compute, backup, network delivery and requests must still be counted.

**Playback delivery:** average bitrate 3 Mb/s is about **1.35 GB per viewing hour** using decimal units. A thousand such viewing hours means roughly **1.35 TB delivered**, regardless of how small the database is. The actual provider/network contract must establish its cost. Do not assume S3 compatibility includes free egress or AWS lifecycle behavior.

## 3. Planning envelopes

Host/worker/observability numbers below are engineering allowances, not researched SKU quotes. Choose a host only after its FFmpeg/filesystem/timeout behavior is validated. Existing account plans might produce a very different invoice.

| Item | Small free beta assumption | Early paid operation assumption |
| --- | ---: | ---: |
| App compute | $15-30 | $40-80 |
| DB compute/storage | ~$5, intermittent | ~$21, continuously active 0.25 CU + 5 GB |
| Separate encoding/job capacity | $10-20 | $20-50 |
| Email | $0 within limits | $20 |
| Observability/backup allowance | $0-10 | $10-30 |
| Example 100 GB object storage | ~$2.30, if metered as above | ~$2.30, if metered as above |
| Subtotal excluding Chat/live/delivery | **~$32-67/month** | **~$113-203/month** |
| Chat | $0 only if eligible and within Build limits | +$499/month if Start monthly is needed |
| Live/video/delivery/domain/payment fees/tax | Additional | Additional |

Thus early paid operation can be **~$612-702/month before video and delivery**, with the illustrated Start Chat subscription. This is why a generic "$20 hosting" estimate would be misleading. User count alone cannot determine total cost.

Suggested decision gates: target a **$100/month non-video beta envelope**, and explicitly approve a **$750/month base envelope** before a paid Chat tier, with separate measured allowances for live usage and delivery. These are proposed caps, not sufficient capacity guarantees. If the business cannot support the Chat floor, restrict/disable that feature or assess alternatives before committing to a migration or annual contract.

No profit, affordability or unit-economics conclusion is possible until expected retained users, session attendance, viewing hours, prices, payment fees and actual provider plans are supplied. Current paid flows produce no verified sales.

## 4. Controls required before spending scales

1. Track connected MAU, concurrent sockets and active users separately. Disconnect on logout/account change; load Chat only where needed.
2. Track participant minutes by call type/resolution and distinguish lesson playback from live usage.
3. Enforce per-user upload GB/day, total stored bytes, maximum video duration/resolution, concurrent transcodes and room capacity/duration.
4. Record raw/generated storage separately; abort expired multipart uploads; delete with verified retention jobs. Reconcile storage inventory to database asset records.
5. Add provider budget alerts at 50/80/100% and application-side quotas where provider hard caps do not exist. Test graceful quota failures.
6. Review database active hours/CPU/connections, slow queries, mail sends/retries/bounces and job backlog weekly during beta.
7. Prove restoration and deletion on a staging bucket/branch. Set explicit history/backup windows and costs.
8. Require an actual account quote and production eligibility check before annual Chat commitments or production traffic.

## 5. Application performance budget

Baseline Lighthouse 13.5.0: root mobile 67 / LCP 5.43s / TBT 458ms; root desktop 98 / LCP 1.08s; login mobile 83 / LCP 4.29s. CLS was zero in each single local sample. Whole-build gzip JS is about 2.04 MiB; root initial script transfer was about 219 KiB. Do not confuse those two sizes.

Proposed release budget: mobile public/auth Lighthouse >=90 in three repeatable runs, no new layout shift, and an initial public-route script target <=200 KiB. Establish authenticated feed/chat/room budgets after staging login works. Measure field p75 LCP/INP/CLS separately; local TBT does not establish INP. Do not introduce an expensive monitoring service without checking its included events, retention and spend limit.
